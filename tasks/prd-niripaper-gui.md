# PRD: niripaper GUI —— 独立桌面壁纸应用

> **这份文档是交给设计工具（本机 open-design）的唯一输入。** 它自包含：读它不需要先读别的文件。
>
> 它按 2026-10-12 的讨论与 2026-10-16 的框架决定更新过。旧版里这些前提**已作废**：
> `config.d/` 多文件合并、壁纸包（`manifest.toml` + 包参数）、`gpui-kit` 工具链、
> "首版不做托盘与自启动"、`hot: false` 这类键、`wallpaper` 是单张。
>
> 实现侧的决定另记在 `tasks/decisions.md`（不随本文件交付）。

## 概述

niripaper 已经有完整的**引擎**：守护进程自己拥有壁纸图层与渲染循环，支持静态图与视频、布局反应式视差、换图过渡，配置是机器可读的（`niripaper schema` / `niripaper state`）。

它缺的只有**前端**：今天要换一张壁纸，用户得手动编辑 `~/.config/niripaper/config.toml`，或者敲 `niripaper set <path>` —— 没有缩略图、不知道有哪些图可选、也不知道当前屏幕上到底是什么。

niripaper 唯一存在过的前端是 Noctalia 插件，**已废弃、不会复活**。本 PRD 描述它的替代品：

一个 **Wallpaper Engine 式桌面应用**，以 niri 为第一目标：壁纸库网格、把壁纸应用到某个输出、属性面板、设置页。

**一条决定性的架构前提：渲染留在守护进程里，应用是守护进程控制 socket 上的薄客户端。** 应用不解码媒体、不碰 GL/EGL/GBM、不自己画壁纸像素 —— 它只读 `schema` / `state` / `query`，只写**意图**（要哪个壁纸、参数是什么）。

## 已定的前提（设计必须尊重）

| 项 | 决定 | 对设计意味着什么 |
| --- | --- | --- |
| 形态 | Wallpaper Engine 式桌面应用：**库网格 + 应用到输出 + 属性面板 + 设置页** | 四个区域，不是"一个设置对话框" |
| 目标平台 | niri 优先，Linux | 单窗口应用，不需要考虑移动/触屏 |
| 渲染位置 | 全部在守护进程；应用是薄客户端 | **应用里没有实时壁纸预览**：预览是守护进程渲染好的 PNG（缩略图/静帧），不是视频播放器 |
| 前端画布 | **原生控件，无 webview** | 界面不能依赖浏览器能力（CSS 滤镜、HTML 视频、字体回退都要另想办法） |
| 交互性 | **静止优先，不做交互壁纸** | niri 的 backdrop 层忽略指针输入，所以"鼠标反应/音频反应"不在范围内 |
| 壁纸 | `wallpaper` 是**列表**（轮播）+ `interval` + `order`，三者都可按输出设 | 属性面板要能表达"这面墙是一个列表 + 播放顺序 + 间隔"，不是单张图 |
| 主题 | 明暗两套，跟随系统；颜色走**语义令牌**，不硬编码颜色值 | 设计用令牌表达颜色，两套主题都要给 |
| 托盘 | **首版就做** | 托盘菜单要有：打开窗口、当前壁纸、暂停/继续、退出 |
| 自启动 | **首版就做**：GUI 静默启动到托盘，取代 niri 的 `spawn-at-startup` | 应用要有"静默启动"这个状态（无窗口，只有托盘） |
| 窗口被完全遮住时 | 守护进程**暂停整个渲染与解码** | 界面上要有办法看出"现在暂停了"（以及为什么） |
| 配置写入者 | 只有一份 `~/.config/niripaper/config.toml`，**只有 GUI 写**；守护进程永远只读 | 设置页是唯一写配置的地方 |
| 不做 | 壁纸包格式（`manifest.toml` / 包参数）、可视化编辑器、资源商城、GPU / MUX 选择 | 库 = 一个目录里的媒体文件，没有"包"这一层 |

## 目标

- 让"换壁纸"不再需要编辑任何文件：从库里选一张 → 应用到某个输出（或全部输出）→ 当场生效（有换图过渡）。
- 让"有哪些壁纸可选"可见：库网格 + 缩略图，缩略图**由守护进程**渲染。
- 让"现在到底是什么状态"可见且可信：实际生效值、来源、屏幕上实际的壁纸 / 类型 / 硬解 / 填充方式、位移与缩放。
- 让全部配置键都能在图形界面里改：界面由 `schema` 驱动，不硬编码键名、取值与范围。
- 让"写配置"这件事**在结构上不可能**触发守护进程自激（见 FR-5）。
- 保持引擎语义不变：视差、总览过渡、换图过渡、填充方式、按输出覆盖全部**原样暴露**，不新增行为、不新增配置键。

## 使用者与场景

| 使用者 | 场景 |
| --- | --- |
| niri 用户（主要） | 装了 niripaper，想看壁纸都有哪些、点一下就换掉，不想再开编辑器 |
| 多输出用户 | DP-1 用这张、eDP-1 用那张；或者一次性把所有输出换掉 |
| 壁纸收藏者 | `~/Pictures/Wallpapers` 下有几十上百张图（含视频），需要缩略图、名字与标记来挑 |
| 调参用户 | 想改缩放 / 跨度 / 过渡效果，又不想记键名与取值范围 |
| 排障的维护者 | 想知道"守护进程现在认为配置来自哪几个文件、实际在画什么"，而不是靠看日志猜 |

## 用户故事

### US-001: 应用外壳与守护进程连接

**描述：** 作为 niri 用户，我打开这个应用就能知道守护进程在不在跑，以及它管着哪些输出。

**验收标准：**
- [ ] 窗口能打开，能渲染一个空的库视图（无壁纸时不崩）。
- [ ] 启动时找唯一那份控制 socket；文件不存在 → 显示"守护进程没在运行"，并支持用参数覆盖 socket 路径。
- [ ] 守护进程没在跑时：界面显示明确的空状态与原因（socket 路径 + "守护进程在运行吗？"这类文案），**不是** panic、不是空白窗口。
- [ ] 连上以后，能从守护进程拿到输出清单并在界面上列出来。
- [ ] 守护进程中途退出/重启：界面在 **5 秒内**变成"未连接"状态，恢复后自动重连，不需要重启应用。

### US-002: `schema` 驱动的设置页

**描述：** 作为调参用户，我要在一个界面里改所有配置键，而且键名、取值范围、单位都由守护进程告诉我。

**验收标准：**
- [ ] 设置页的每一项都来自守护进程给的 `schema`，代码里**没有**任何键名字面量、取值范围或选项列表。
- [ ] 每种取值类型都有对应控件：开关；数字输入（带上下限，无上限要能表达）；路径选择；文本；下拉；多选；一组固定个数的数字；动画（三选一：关 / 缓动时长+曲线 / 弹簧）。
- [ ] 每个控件显示该键的说明文字作为提示，在数值非平凡时显示单位。
- [ ] 遇到不认识的类型：**跳过该键并显示一行说明**，不猜控件、不崩溃。
- [ ] 下拉与多选的选项直接取 `schema` 给的列表（例如过渡效果的 9 个效果、niri 的 5 条曲线），不写死。
- [ ] 设置页要能容纳几十个键而不变成一堵墙：分节、可搜索、显示"已改动"标记。

### US-003: 改设置当场生效

**描述：** 作为用户，我改完设置后，守护进程当场按新值工作。

**验收标准：**
- [ ] 设置写入**唯一那份** `~/.config/niripaper/config.toml`（守护进程只读它）；不改任何其他工具的配置。
- [ ] 写入是外科手术式的（只动被改的键）+ 原子替换（写临时文件再改名）：任何时刻磁盘上的文件都是完整可解析的。
- [ ] 改一个值后，守护进程热重载并生效：实际生效值立刻变成新值，**不需要重启守护进程**。
- [ ] 写入的只有**意图**（用户选了什么），文件内容里不含任何来自守护进程的"当前值"。
- [ ] **回归（自激振荡）：** 界面开着、用户不动任何东西时，连续 10 秒内对该配置文件算哈希，**0 次变化**；相同条件下守护进程日志里 `config reloaded` 出现 **0 次**。
- [ ] 代码里不存在"读守护进程状态 → 生成配置内容"的路径（状态只用于显示与校验）。

### US-004: 按输出白名单路由写入

**描述：** 作为多输出用户，我要能只给一块屏设壁纸与参数，其余输出不受影响。

**验收标准：**
- [ ] 应用启动时从 `schema` 读出**哪些键可以按输出设**（当前 5 个：壁纸列表 / 缩放 / 横向跨度 / 纵向跨度 / 填充方式），并以它决定每个键写到哪一层。
- [ ] 这 5 个键之外的任何键**永不**出现在按输出的表下，一律写在文件顶层。
- [ ] 按输出的表里的键名与守护进程报出的输出名逐字一致；界面上的输出列表**只能来自**守护进程，不能让用户手打一个不存在的名字。
- [ ] 反例回归：手工构造一份"把全局键写进按输出的表"的文件时，守护进程会**拒绝整个文件**（保留旧配置并报错）——应用必须不产生这种文件。
- [ ] 只给一块屏设了壁纸时，另一块屏的壁纸不变。

### US-005: 只读状态视图（实际生效值与来源）

**描述：** 作为用户/维护者，我要一眼看到守护进程**实际**在用什么值，以及这个值是从哪来的。

**验收标准：**
- [ ] 展示实际生效值、这份配置由哪几个来源合成、以及哪些值来自 niri 的配置。
- [ ] 当"文件里写的值"与"实际生效值"不一致时，界面必须显示**实际生效值**并说明来源（显式值 > niri 配置 > 内置默认值）。
- [ ] 展示屏幕上实际的壁纸路径、类型、硬解方式、填充方式（**实际**用的值，例如视频 + 平铺会报回填满）。
- [ ] 展示横向/纵向位移、缩放、画布尺寸。
- [ ] 这个视图**没有**任何回写路径：在它上面点任何东西都不会改配置、不会改变屏幕内容。
- [ ] 值来自守护进程，不是本地缓存的旧值：守护进程改值后，视图在 **2 秒内**跟上。

### US-006: 守护进程能列出库内容

**描述：** 作为应用，我需要一份机器可读的"库里有哪些媒体文件"。

**验收标准：**
- [ ] 应用能从守护进程拿到库清单：每个条目至少有稳定的 id、名字、类型（图片/视频）、以及文件路径。
- [ ] id 稳定、无空格、可作为"取缩略图"的引用。
- [ ] 库目录不存在或为空时返回空列表，不算失败、不报错。
- [ ] 库 = 一个目录里的媒体文件（无"包"这一层）：扫描要跳过不支持的文件，并说明跳过了什么。

### US-007: 缩略图由守护进程渲染

**描述：** 作为应用，我要缩略图，但我不想在自己的进程里解码媒体或碰 GL。

**验收标准：**
- [ ] 应用能按 id 向守护进程要一张缩略图（可指定宽高），拿到一张 PNG 的路径；失败时拿到明确错误。
- [ ] 缩略图由守护进程渲染：它已经有解码器与 GL，且已经按合成器反馈钉好了 GPU 与 EGL vendor（一个进程只能钉一个 vendor）。应用进程**不**链接解码库、不做图片解码、不建 GL 上下文。
- [ ] 指定宽高时输出尺寸就是它；省略时用默认尺寸。
- [ ] 生成缩略图**不打扰屏幕上的壁纸**：正在跑的视差/换图过渡不中断，屏幕上的壁纸路径不变。
- [ ] 未知 id、非法宽高返回明确错误（不是崩溃、不是空图）。
- [ ] 连续请求同一个 id 两次不泄漏内存与文件句柄。

### US-008: 库的扫描与稳定顺序

**描述：** 作为壁纸收藏者，我要库里的东西每次打开都一样，坏文件不要拖垮整个库。

**验收标准：**
- [ ] 库里的条目顺序**稳定**：同一份库两次打开顺序相同（按名字排序，而不是按文件系统返回顺序）。
- [ ] 单个文件坏掉（无法解码、扩展名不支持）：跳过它并说明原因，不影响其他条目，不让整个库列表失败。
- [ ] 库目录在应用运行时被增删文件：**10 秒内**反映到网格，或明确提供刷新动作。
- [ ] 库为空时显示空状态文案（含库目录路径），不是空白。

### US-009: 库网格视图

**描述：** 作为用户，我要在一个网格里看缩略图挑壁纸。

**验收标准：**
- [ ] 网格里每一项显示：缩略图、名字、标记（视频/图片、尺寸等），选中态清晰。
- [ ] 缩略图**不在 UI 线程上同步等**：先出占位，PNG 到位后再替换（等待期间界面可交互）。
- [ ] **虚拟化**：库里放 200 个条目时滚动流畅，不一次性渲染 200 张图。
- [ ] 缩略图有缓存，重复滚动不重复请求同一个 id。
- [ ] 网格要能表达"这一张正在某块屏上"（对应 US-005 的状态）。
- [ ] 大库（数百项）下滚动时，缩略图请求要有节制（不能因为快速滚动把守护进程打满）。

### US-010: 把壁纸应用到输出

**描述：** 作为多输出用户，我要把这面墙的壁纸应用到某一块屏（或者所有屏）。

**验收标准：**
- [ ] 网格里选中一个条目后，能把它的壁纸应用到：某一个输出、或全部输出。
- [ ] 界面上**必须**写清两种语义的区别，且两条路都要有：**临时覆盖**（任何一次热重载都会盖掉它）与**持久设置**（写配置文件）。
- [ ] 持久设置写的是**壁纸列表**：能把多个条目组成一面墙的列表，并设置播放顺序与间隔（US-004 的 5 个可按输出设的键之一）。
- [ ] 临时生效当场可见：换图过渡照常播（不因为换壁纸路径而退化）。
- [ ] 点一个不存在的输出：显示守护进程报的错，不静默失败。
- [ ] 界面上"现在屏幕上是哪张"与守护进程报的一致，而不只是与刚才点了什么一致。

### US-011: 属性面板

**描述：** 作为调参用户，我要选中一个壁纸后就地调它的参数，而不是先跳到设置页。

**验收标准：**
- [ ] 选中条目后，属性面板渲染与它相关的配置键（至少填充方式、缩放；多输出时含按输出的覆盖）。
- [ ] 面板与设置页**共用**同一套控件映射，没有第二条渲染路径。
- [ ] 能预览**临时**效果与**持久**效果（对应 US-010 的两种语义），并在界面上标明哪个是哪个。
- [ ] 参数改动后，实际生效值或屏幕上的壁纸在 **2 秒内**反映出来。
- [ ] 面板上的值变化**不会**引发 US-003 的振荡回归（空闲 10 秒文件哈希 0 次变化）。

### US-012: 现代外观与主题

**描述：** 作为用户，我要一个看起来 2026 年而不是 1996 年的界面。

**验收标准：**
- [ ] 明暗两套主题都能切换，切换后所有界面文字与背景的对比度可读（不出现白底白字）。
- [ ] 界面只用**语义令牌**表达颜色（背景 / 前景 / 边框 / 表面 / 次要 / 强调…），不硬编码颜色值。
- [ ] 跟随系统主题：系统切换时界面跟着变，不需要重启应用。
- [ ] 重复元素的 id 由领域值派生（条目 id、输出的 connector 名），不是列表下标。
- [ ] 视觉密度：缩略图是主体，参数用表单，**不用模态对话框承载日常操作**。

### US-013: 异常与空状态

**描述：** 作为用户，出问题时我要看到一句人话，而不是一个空白窗口。

**验收标准：**
- [ ] 至少这些状态各有明确界面：守护进程没在跑、socket 陈旧（存在但没人应答）、库为空、某个文件坏掉、缩略图失败、某块输出没有壁纸、配置写入被守护进程拒绝。
- [ ] 每种状态都写明**接下来能做什么**（例如"启动守护进程"的命令行），而不只是报错。
- [ ] 守护进程拒绝一份配置（解析失败、保留旧配置）时，界面能显示这次失败，并保持"当前生效值"与守护进程一致，不显示刚写进去的错值。
- [ ] 任何异常都不使应用退出；恢复条件满足后界面自动回到正常态。

### US-014: 托盘与静默启动

**描述：** 作为用户，我要这个应用像桌面应用那样待着，而不是每次都得开一个窗口。

**验收标准：**
- [ ] 应用能**静默启动**（无窗口，只有托盘图标），这是自启动时的默认行为。
- [ ] 托盘菜单至少有：打开窗口、当前壁纸（一眼看到现在是什么）、暂停/继续、退出。
- [ ] 托盘图标能反映状态：守护进程没在跑时与正常时看得出区别。
- [ ] 关闭窗口不退出应用（退到托盘），退出只能从托盘菜单走。
- [ ] 应用提供"开机自启"的开关，并且写的是它自己的自启动项（不再依赖 niri 的 `spawn-at-startup`）。

## 功能需求

- FR-1: 应用是守护进程的**薄客户端**：壁纸的渲染、解码、GL/EGL/GBM 与 dmabuf 全部留在守护进程；应用进程不得链接解码库、不得解码媒体、不得自己绘制壁纸像素，预览一律来自守护进程输出的 PNG。
- FR-2: 应用只通过既有控制 socket 与守护进程通信（一行进一行出，全会话一份，请求里带输出名）；socket 不存在即"守护进程没在运行"，并支持用参数覆盖路径。
- FR-3: 应用的界面**必须**由 `schema` 驱动：键名、类型、范围、单位、默认值、说明、可选项全部取自守护进程，代码中不得硬编码任何键名或取值列表；不认识的类型跳过而不是猜。
- FR-4: 应用**必须**按 `schema` 给出的"可按输出设"白名单路由写入：只有白名单里的键可以写在按输出的表下，其他所有键必须写在文件顶层。理由（硬约束）：把全局键写进按输出的表会让守护进程**拒绝整个配置文件**。
- FR-5: 应用**必须只写意图**，永不把守护进程报出来的值写回它自己的输入。状态查询的返回值只用于显示与校验，不得成为生成配置内容的来源。（这是已实测过的自激振荡失败模式：连续每 ~2 秒翻转、10 秒内 7 次重载。）
- FR-6: 应用**必须**把设置写在唯一那份 `~/.config/niripaper/config.toml` 里，不改任何其他工具的配置；写入必须外科手术式 + 原子替换。
- FR-7: 应用**必须**在界面上区分两种改壁纸的语义：临时覆盖（任何一次热重载都会盖掉它）与持久设置（写配置文件）。
- FR-8: 守护进程**必须**能列出库内容，一行 JSON：库 = 一个目录里的媒体文件，条目含稳定 id、名字、类型、路径。
- FR-9: 守护进程**必须**能按 id 渲染缩略图（可指定尺寸）并写出 PNG。理由：守护进程已经有解码器、GL 与"按合成器反馈钉好的目标 GPU / EGL vendor"，缩略图属于那里，不属于 GUI 进程。
- FR-10: 界面上可供选择的输出**必须**来自守护进程报出的输出列表，不得由用户手打；应用到不存在输出时必须显示守护进程返回的错误。
- FR-11: 应用**必须**原样暴露既有的运动与过渡键，不得新增行为、不得新增配置键、不得在应用侧重新解释这些语义。
- FR-12: 应用**不得**修改 niri 或任何桌面壳的配置、不得写入 layer rule、不得代管"壁纸进 backdrop"或"工作区背景"这两种放置方式；它们继续由用户与 niri 决定。
- FR-13: 应用**不得**提供任何 GPU / 渲染设备 / MUX 选择项（选哪块卡是合成器的决定）。
- FR-14: 守护进程断开或重启时，应用**必须**显示明确状态并在恢复后自动重连，不得退出、不得把上一份可能过期的值当作当前值显示。
- FR-15: 应用**必须**在写完后核对效果：读回状态确认该值确实生效；若守护进程保留了旧配置（解析失败），向用户报出这次失败并把界面回到实际生效值。
- FR-16: 应用窗口空闲时**不得**轮询守护进程到产生持续负载；静止状态下的请求频率必须有上界。
- FR-17: 应用**必须**支持静默启动到托盘（无窗口），关闭窗口不退出；托盘菜单提供打开窗口、当前壁纸、暂停/继续、退出。
- FR-18: 应用**必须**提供开机自启开关，写自己的自启动项，不依赖 niri 的 `spawn-at-startup`。
- FR-19: 应用代码遵守本仓库的构建与自检约定（格式、静态检查 0 警告、测试全绿）—— 这条是仓库级要求，不构成界面设计约束。

## 非目标（明确不做）

- **不做** shader / 粒子 / 交互式场景壁纸（niri 的 backdrop 层忽略指针输入，与"静止"互斥）。
- **不做**音频反应、鼠标反应特效。
- **不做**壁纸包格式（`manifest.toml`、包参数）：库就是一个目录里的媒体文件。
- **不做**壁纸资源商城 / store。
- **不做**可视化编辑器（不编辑文件、不做效果设计器）。
- **不做** Wallpaper Engine 格式兼容（不读它的包与项目文件；只借"填充方式"的名字）。
- **不做**任何 GPU / MUX 选择。
- **不改**守护进程的运动语义：视差、总览过渡、换图过渡照旧；应用只是它们的遥控器。
- **不**复活、**不**修改 Noctalia 插件。
- **不**替代合成器自己的壁纸处理：壁纸进 backdrop、静态 backdrop 与背景色的现状不变，应用不写 layer rule、不改 niri 配置。
- **不**做库目录的写入/导入工具（首版只读库）。

## 设计考虑

形态照 Wallpaper Engine 的桌面应用（以 niri 为第一目标），四个区域：

1. **库网格**：缩略图 + 名字 + 标记，虚拟化滚动，选中即进属性面板。
2. **应用到输出**：输出清单来自守护进程；可"只这一块"或"全部"；临时与持久两条路各自可见（FR-7）。
3. **属性面板**：与设置页共用同一套控件；守护进程给的说明文字直接当提示、单位直接当单位。
4. **设置页**：全部键按 `schema` 的顺序分节；可按输出设的键在选中某个输出时出现（FR-4）。

外加两个非窗口表面：**托盘菜单**（US-014）与**静默启动状态**。

**视觉目标：** 现代、密度适中、信息优先 —— 缩略图是主体，参数用表单，不用模态对话框承载日常操作。重复元素用领域 id（条目 id、输出名），不用列表下标。

**能力边界（这套原生控件能画什么）。** 界面用的是原生 UI 工具包（Go，GPU 自绘，无 webview），社区组件库覆盖：网格视图、虚拟化列表、表格、树、侧栏、页签、分栏、对话框/抽屉/气泡/提示、命令面板、表单与字段、进度/骨架/空状态、图表、日期与颜色选择、Markdown 与代码高亮、图片与图标、以及弹簧/关键帧/过渡这类动画。**设计可以直接用这些控件表达，不必自创。**

**已知缺口：没有视频组件。** 原生工具包与社区组件库里**都没有视频播放**，所以视频壁纸**不能在应用里播放预览**。设计上按这样处理：

- 视频条目与图片条目一样，用**一张静帧缩略图**代表（由守护进程抽帧）；
- 需要"动起来"的地方（例如应用某张视频壁纸前的确认），用**逐帧/多帧静图**或一个短循环的帧序列表达，而不是内嵌播放器；
- 唯一例外是一条**局部逃生口**：可以把**某一个**区域嵌成 web 页（工具包支持在原生 UI 之上叠一个 web 视图），只在确实需要播放时用 —— 默认不用。

**建议的设计方向。** open-design 自带 5 套设计方向：`modern-minimal`（Linear / Vercel）、`editorial-monocle`、`human-approachable`、`tech-utility`、`brutalist-experimental`。本应用的气质与 `modern-minimal` 最贴（现代、密度适中、信息优先），`tech-utility` 次之。**具体选哪套由你定**，但请在两套主题（明/暗）下都成立。

**期望的交付物。** open-design 的 **`prototype`** 模式：一个可跑的原型，覆盖上面四个区域 + 托盘菜单 + US-013 的空状态与异常态。参数不用真接守护进程 —— 用假数据把交互与视觉走通即可（真实数据来自 `schema` / `state`，形态稳定）。

## 技术考虑

- **后端已经就位，不需要改**（首版除两个新动词外）：机器可读的 `schema`（配置键）、`state`（实际生效值 + 来源 + 屏幕上是什么）、`set <输出|*> <路径>`、`query`、以及配置文件的热重载。多输出由一个进程按输出寻址。
- **两个新动词是唯一的守护进程改动**：列出库内容、渲染缩略图（FR-8、FR-9）。协议是一行进一行出，所以两者都只能回一行。
- **临时覆盖的语义**：`set` 是临时的，任何一次热重载都会盖掉它。持久设置只有一条路 —— 写配置文件。
- **为什么缩略图必须在守护进程**：它已经按合成器反馈开好了渲染栈并钉好了一个厂商的驱动；而"一个进程只能钉一个厂商"。GUI 进程再建一套渲染栈等于把已经踩平的坑重新挖一遍。
- **振荡失败模式的教训直接约束数据流**：意图（用户选了什么）与镜像（守护进程报了什么）必须是两张表，只有意图写进配置（FR-5）。验收用"空闲时文件哈希 0 次变化"来钉。
- **配置文件是逐份解析的**：出错能指名位置，失败保留旧配置并打印原因，且解析失败不许把守护进程打挂。应用因此必须能显示"这次写入被拒了"（FR-15）。
- **工具链**：**Tauri v2**，界面走 **web 前端**（系统 webview，Linux 上是 WebKitGTK），前端复用已完成的 `tasks/prototype-ui.html`。理由与实测见 `tasks/decisions.md` 〇：网页版原型的观感就是要的那一版，而景深模糊、径向渐变、z-index 置顶、平滑动画这些在浏览器里是天生就有的，原生手绘要一件件重造；且引擎本就是 Rust，GUI 用 Rust 是同一套工具链。依赖规模实测 `Cargo.lock` 408 个包（比记过的 gpui-kit 849 个少一半）；本机系统依赖已齐备。托盘/静默启动（US-014）由 Tauri v2 内置托盘承担。**`CARGO_TARGET_DIR` 必须指到 `/home` 下**（本机 `/tmp` 是 7.8 GB tmpfs，撑爆过）。
- 应用是**独立进程**，因此与守护进程的"一个进程一个厂商"约束互不干扰；但这也意味着应用绝不能把自己变成第二个渲染器（FR-1）。

## 成功指标

- 换一张壁纸：**0** 次手动编辑文件，**≤3** 次点击/按键（库 → 选条目 → 选输出）。
- 新增一个配置键：应用侧 **0** 行 UI 代码改动（`schema` 驱动，FR-3）。
- 自激振荡回归：空闲 10 秒配置文件哈希 **0** 次变化、守护进程重载 **0** 次。
- 库 **200** 个条目时滚动不掉帧到不可用（虚拟化生效，US-009）。
- 守护进程断开到界面反映：**≤5** 秒（US-001）；守护进程改值到界面跟上：**≤2** 秒（US-005）。
- 属性面板与设置页渲染同一批键时不产生两套控件实现（US-011）。
- 首版功能齐备：四个区域 + 托盘 + 静默启动 + 自启开关，且 US-013 列的每种异常态都有界面。

## 开放问题

1. **应用住在哪里**：本仓库新增一个 **Rust crate / 二进制**（与守护进程共享 schema 与协议类型的定义），还是另开一个仓库？（实现侧已倾向前者：`niripaper-app/`，与守护进程并列。）
2. **库根目录**：需要一个约定路径（建议 `$XDG_DATA_HOME/niripaper/library`，或让用户配置），以及"库目录不存在"时的行为。
3. **缩略图缓存**：落在哪（XDG cache 目录？）、什么键失效（文件 mtime？），以及库变大时的清理策略。
4. **应用是否负责拉起守护进程**：建议**不**（只提示 + 给出命令行），避免应用与自启动两套生命周期打架 —— 需要确认。
5. **缩略图的默认尺寸**，以及守护进程没画任何输出时能否出图（无头降级路径）。
6. **空闲轮询上界**（FR-16）：具体间隔，以及是否改成事件驱动（守护进程何时需要主动告知"状态变了"）。
7. **托盘菜单的最终条目**：暂停/继续指的是"暂停渲染"还是"暂停轮播"，两者都要吗？
