# 已知陷阱与失败模式

这些是**实测**得来的经验结论（不是设计推测），每条给出「出了什么问题 → 机制 → 怎么发现」。要自己动手量之前先看 [`./verification.md`](./verification.md)：量法本身也会骗人（见风险 13）。名词（backdrop / canvas / snapshot / layer / output…）见 [`../CONTEXT.md`](../CONTEXT.md)。

编号是稳定标识，跨文件引用按编号指代；本文件按现象分组，所以组内编号不连续。

## GPU 与设备选择

### 风险 1：选错 GPU（这条判断本身被实测修正过）

**现象**：屏幕上一个像素都不出，但没有任何报错。

**机制（修正后）**：不是"输出在哪个 GPU 上，就在哪个 GPU 上渲染"。niri 用**主渲染节点**合成所有输出，再把结果拷贝给"仅显示"设备。所以正确规则是：

> **跟随合成器的 dmabuf feedback `main_device`**：`surface feedback main device` 指向哪个 `dev_t`，就在那个节点上开 GBM/EGL。

在"输出所在的那块 GPU"上渲染反而会每帧多一次跨 GPU 导入 + 拷贝。

**为什么静默**：跨设备提交非 LINEAR 缓冲时，niri 不报错、`wl_buffer::release` 也正常回来，但画面上什么都没有。

**怎么发现**：先量"模糊区 / 壁纸区四段均值"（方法见 [`./verification.md`](./verification.md)），不要只看有没有报错。

> ⚠️ **被推翻的旧判断**：早期写的是"输出在哪个 GPU 就在哪里渲染"；实测后改为上面这条"跟随合成器 `main_device`"。凡是看到"按输出选卡"的说法，都是被修正前的版本。

相关的决策（不做选卡开关、不碰 MUX/BIOS）见 [`./SPEC.md` §2](./SPEC.md#2-已定决策无需再议)。

### 风险 2：一个进程只能钉一个 EGL vendor

**机制**：GLVND 只在**第一次 EGL 调用**时读 `__EGL_VENDOR_LIBRARY_FILENAMES`，之后不再改。vendor 由目标 GPU 的 PCI vendor id 决定（见 [`./SPEC.md` §2](./SPEC.md#2-已定决策无需再议)）。

**结论**：合成器的 main device 是**单一** GPU，所以"一个进程钉一个 vendor"够用；但**不要**设计成"一个进程同时渲染两块不同厂商的 GPU"。

**怎么发现**：没有干净的可诊断报错可依赖 —— 钉错 vendor 的表现与风险 1 同级的静默失败（能拿到 display 却拿不到可用 config／画面不出）。所以这条只能靠**设计上禁止**，不能靠事后排查。

### 风险 11：LINEAR 是跨设备 scanout 的通行证（后半句已被实测推翻）

**机制**：niri 对"渲染节点 ≠ 主节点"的输出只接受 **Linear** 的 scanout tranche。我们选 LINEAR（Mesa 能渲染进 LINEAR），既省一次拷贝又保证可直扫。

**原判断**（⚠️ 已被推翻）：NVIDIA 不能渲染 LINEAR，所以若将来 main device 是 NVIDIA，必须改用它的 tiled modifier，并接受 niri 的跨设备拷贝。

**实测（2026-10-06，真切到 dGPU-only 之后）**：**后半句是多虑，不用改代码。** `Pool::new` 的候选搜索本来就会落到 NVIDIA 能渲染的 modifier 上 —— 日志 `2560x1440 XR24 via NVIDIA [EGL_PLATFORM_GBM_KHR] (nv:0x0300000000606010)`，**`rejected` 行数为 0**（第一个候选就成功），而且 `gbm.rs` 那面 `GBM_BO_USE_LINEAR` 与 tiled modifier **共存无碍**。另外此时**没有**跨设备拷贝：渲染节点与输出同卡。

**怎么发现**：看启动日志里 `… via <vendor> [<EGL platform>] (<modifier>)` 那一行与 `rejected` 行数 —— 若堆了一串 rejected 或最终落到渲染不了的 modifier，就是踩到这条。

## 运动与视差回归

与视差有关的**规格级**回归（竖直切换带着横向一起滑 → 斜向、纵向进度随工作区总数变化、总览里的横向冻结、过期的 `is_focused` 把焦点抢回去）连同它们的修正与实测数据，写在 [`./SPEC.md` 的「实现注记」（§4.4）](./SPEC.md#44-实现注记)，本文件不重复。下面是调试手法相通的几条。

### 风险 3：进度按"实际列数"归一化

**现象**：开 / 关任何窗口都会让壁纸移动，视差比例也跟着变。

**机制**：进度若按"该工作区**实际**列数归一化"，列数一变，同一个焦点列算出来的位置就变。

**修法**：必须用固定跨度 `span`（横向 `column_span`、纵向 `workspace_span`，见 [`./SPEC.md` §4.2](./SPEC.md#4-运动规格必须实现的语义)）。纵向那一轴当初漏了同样的道理，成因见 SPEC §4.4 第 10 条。

**怎么发现**：开一个窗口，看壁纸是否动。

### 风险 4：重复下发相同的目标

**现象**：画面在移动中"突然停住"。

**机制**：重复下发**与当前目标相同**的目标 → 缓动被重启（参考实现里 `Behavior` 只在源值变化时才动；多发一次等于重新开一段缓出）。

**修法**：只在目标**变化**时下发。另一个同源的坑：判断"播放器 / 客户端身份"不能用浮点 mtime 比较 —— 末位抖动会让每个 tick 都判成新客户端，于是每秒重发一次目标；要量化后再比。

**怎么发现**：`--trace` 的逐帧输出里，目标值没变却出现了新的一段动画。

### 风险 5：中途改目标未从当前位置缓出

**现象**：画面会跳一下。

**机制**：动画走到一半时换目标，若从"起点"重新缓出而不是从"当前已到达的位置"缓出，位置就不连续。

**修法**：先取当前值，再换目标。

**怎么发现**：`--trace` 里改目标的那一帧 `offset` 出现跳变。

### 风险 10：弹簧的"结束"判据不能用瞬时误差

**现象**：看不到回弹 —— 动画在过冲之前就停住（本机实测：轨迹一路走到 `0.9600` 直接停住）。

**机制**：欠阻尼弹簧每半个周期穿过一次目标，`|当前 − 目标|` 会在**第一次**穿越时变成 0。用它当结束判据，动画就在过冲之前被判结束，用户永远看不到回弹。

**修法**：判据用**衰减包络**（ζ<1 时 `e^{-ζωt}/√(1-ζ²)`），它单调递减；值本身该过冲就过冲。

**怎么发现**：看轨迹有没有过冲 / 回弹。修好后实测过冲 **0.0065**，与解析值 `e^{-πζ/√(1-ζ²)}×0.04` 一致。

总览过渡用的就是弹簧（见 [`./SPEC.md` §2](./SPEC.md#2-已定决策无需再议)），所以这条对总览同样成立。

## backdrop、层序与原生层交接

### 风险 8：backdrop 内的层序取决于创建顺序

**现象**：视差"失效" —— 壁纸不跟随。

**机制**：同一层里谁盖住谁取决于**创建顺序**，被别的层盖住的层当然看不到自己的移动。这跟视差算法无关。

**怎么发现（按顺序排查）**：

1. 先查是否有别的层盖住：`niri msg --json layers`；
2. 再做位移测量（方法见 [`./verification.md`](./verification.md)）；
3. **最后**才怀疑算法。

### 风险 7：backdrop 一致性有固有每帧成本

**机制**：壁纸每动一帧，backdrop 就失效 → niri 要重建并重跑模糊。这是"窗口背景必须跟随壁纸"的代价，**无法消除**。可省的是：额外的解码 / 渲染开销、跨 GPU 拷贝、外部进程往返、GPU 选错（风险 1）。

**怎么发现**：成本只在壁纸移动时按帧计价，别拿静止时的开销推断移动时的手感或开销。放置位置（工作区背景 vs backdrop）与模糊效果的关系见 [`./SPEC.md` §2](./SPEC.md#2-已定决策无需再议)。

### 风险 6：`setWallpaperEnabled` 的恢复不可靠

**现象**：壁纸变纯色（原生壁纸层没被恢复）。

**机制**：`setWallpaperEnabled(connector, bool)` 是**运行时**开关，在 `onExit` 里调用不一定生效（那时运行时正在拆卸）。

**缓解**：插件启动时对**全部**输出自愈式恢复 `true`；文档写明"万一壁纸变纯色就重启 Noctalia"。交接语义见 [`./SPEC.md` §2](./SPEC.md#2-已定决策无需再议)。

## 缓冲生命周期

### 风险 9：`wl_buffer::release` 的语义

**现象**：等 `wl_buffer::release` 永远等不到，缓冲池卡住。

**机制**：`release` 只在缓冲**被替换**之后到来 —— 只有一个缓冲常驻屏幕上时，合成器不会释放它。

**修法**：按"**替换后才回收**"来设计池（管线深度 ≥ 1）。

**怎么发现**：提交 N 帧只等到 N−1 次 release；只提交 1 帧并让它常驻时，一次都不会回来。

## 视频

### 风险 12：外部进程的视频帧拿不到

**现象**：换图过渡时视频那一侧混不进去。

**机制**：用**外部** `mpvpaper` 进程时拿不到它渲染的帧，无法与另一侧混合。

**现行方案**：视频走 V2 —— 守护进程内嵌 libmpv（`mpv_render_context` + OpenGL），帧就在自己进程里，于是可以快照 + 混合（见 [`./SPEC.md` §2 的「视频方案」](./SPEC.md#2-已定决策无需再议) 与 §3 的"双后端、单循环"）。换句话说：这条风险只在"拉起外部播放器进程"的方案里成立。

## 测量可信性

### 风险 13：不可信的指标

**现象**：拿噪声当结论，宣称"更省"或"更流畅"。

**机制**：`--dump-stats` 是**抽样**输出（不能用来数帧率）；`nvidia-smi` 在桌面日常负载下噪声极大（难以量测边际成本）。

**做法**：先用 [`./verification.md`](./verification.md) 的方法确认指标可信，再下结论。

## 分发与 soname

### 风险 14：预编译二进制被钉在构建它的发行版上

**现象**：Release 的二进制在别的机器上起不来（`libmpv.so.X` 找不到），而 workflow 全绿。

**机制**：链接 `libmpv` 的进程，soname 就是**发行版 ABI** —— Ubuntu 22.04 是 `libmpv.so.1`（mpv 0.34），Arch 是 `libmpv.so.2`（0.41）。**workflow 自己抓不到**：构建机上当然有它链接的那个 soname，只有把产物**下载到别的机器上跑**才看得见。

**踩到的实例**：第一版发的 `-x86_64-linux` 就是这么错的（名字还宣称通用 Linux）。

**修法**：**按链接的库命名**（`-x86_64-linux-gnu-mpv0.34` / `-mpv0.41`），**不要按发行版命名**。文件名里写发行版会被读成"只有那个发行版能用"，而实测两份构建要的 glibc **完全相同**（都是 2.34），唯一差别就是 libmpv 的 soname —— 名字就该说这件事。构建它的发行版写进包内的 `INSTALL.txt`，而且那里的 glibc / soname 必须是 **workflow 量出来的**（`objdump -T` / `ldd`），不是手写的（手写必然过时）。

**怎么发现**：把产物真下载下来在**别的机器**上跑（步骤见 [`./verification.md`](./verification.md)）—— 只看 workflow 绿抓不到这条。

## git 历史与工作副本

### 风险 15：跨过"把文件移出索引"的那次提交做历史操作，会覆盖工作副本

**现象**：本地文档的工作副本被旧内容盖掉，或被直接删掉。

**机制**：一个**曾经被跟踪、后来从索引移除**的文件，其旧版本仍留在更早的提交树里。于是：

* 往回 `checkout`（或任何会 checkout 到旧提交的操作）会把**旧版本从 git 里还原出来**，盖掉工作副本；
* 往前跨过"删除它的那个提交"又会让文件在工作树里消失；
* `git rebase -i <共同根>`（改写 `main` 历史时必然要跑）**两头都占**。

本仓库的实例：`.gitignore` 化的那次提交是 `a287e6b`（「HANDOFF.md 不进仓库」），而 `ab4be5a` 及此后十几个提交的树里都还有 `HANDOFF.md`，正是 `a287e6b` 把它从索引里删掉的。

**怎么发现（复现）**：`git log --all -- <文件>` 能列出这一串；随便 checkout 一个旧的，再看工作树。

**处置**：本地事实放在仓库**外面**（`~/workspace/rust/niripaperdocs/`），任何 git 命令都够不到。仓库里不再有这类工作副本（`HANDOFF.md` 已于 2026-10-12 删除）。在仓库里编辑这类文件前，先确认没跑过 rebase。

**一般化**：凡"曾经进过索引、后来只作为本地工作文件存在"的东西都适用 —— 权威副本要么在仓库外，要么在它被跟踪的那段历史之外。

## 容器里的 gh

### 风险 16：容器 job 里 `gh` 需要 `--repo`

**现象**：release job 到 `gh release …` 那一步报 `failed to run git: not a git repository`。

**机制**：`gh` 不只要有 `git` 在 PATH 上（Arch 的 `base-devel` **不含** git，得单独装），还要能**从 git 仓库认出是哪个 repo** —— 容器里认不出来。

**修法**：`.github/attach-release.sh` 的三次调用都显式带 `--repo "$GITHUB_REPOSITORY"`。

**怎么发现（本地可复现）**：在一个**不是 git 仓库**的目录里跑 `gh release view <tag>` 会给出同样的错，加上 `--repo` 立刻正常 —— 当初就是这么验证修法的。

## 别把输出写回输入

### 风险 17：别把"镜像"写回输入

**现象**（2026-10-06 实测，Noctalia 插件侧）：每 ~2 秒翻一次，10 秒里 7 次 `config reloaded`，日志里 `wallpaper → …` 成对出现。

**机制**：那个工具曾把 `effective` 写进配置的 `[outputs."X"] wallpaper`，而 `effective` 同时又是"daemon 现在在画什么"的**镜像** —— 于是 daemon 的**输出**被喂回它自己的**输入**：两个来源差一步就永远来回翻，每翻一次就是一次**拆旧媒体 + 建新媒体**。

**修法**：把**意图**（用户选了什么）和**镜像**（daemon 报了什么）分成两张表，只有意图写进配置。

**怎么发现**：idle 时反复算那份生成文件的哈希 —— 变了就是在自激。

**一般化**：凡是"根据程序输出生成它的输入"的地方都适用。

## 帧回调与动画推进

### 风险 18：动画一帧都不走 —— 帧请求必须跟着 `commit`

**现象**：动画完全不推进，且没有任何报错，看起来像"渲染循环没跑"。

**机制**：`wl_surface.frame` 只在 `wl_surface.commit` 时生效。单独发出帧请求、**不 commit**，那个回调永远不来。正确做法是不管有没有新 buffer 都要 commit：有 buffer 就与它同一次 commit；缓冲池空时补一次**只带帧请求的 commit**。

**相关的另一半**：缓冲池空时**不能只"跳过绘制"** —— 那样既没有 commit 也没有新的帧请求，动画会卡死（从"没画"变成"永远不画"）。必须补上那次 commit。

**怎么发现**：`--trace` 里帧数与目标值都不动，但进程在 poll() 上醒着；对照"有没有 commit"就能定位。

**节奏（实测）**：niri 对图层表面的 frame callback 按 **60 Hz** 节奏派发，即便输出本身是 180 Hz（实测 68 帧的 dt：min 15.9 / 中位 16.7 / max 16.9 ms）。所以 600 ms 的缓动大约 36 帧；视频的 `video_fps` 上限之所以建议 25–30 也与此有关 —— 每出一帧都会作废一次 backdrop 模糊。

## 配置热重载

### 风险 19：写配置再发 `set`，重载会打断正在播的过渡

**现象**：从桌面应用换壁纸，画面直接跳到新图，没有过渡；用命令行 `niripaper set` 换却正常。

**机制**：应用换壁纸要做两件事，先写 `config.toml`（重启后还在），再发 `set`（立刻换）。守护进程收到 `set` 开始播过渡，紧接着 inotify 报告配置变了，重载时**无条件重建过渡对象**，正在播的那次就被丢掉。两件事谁先到不固定：重载先到时会先换一次图，`set` 再换一次，过渡从半帧重新开始。

**修法**：重载只在过渡设置**真的变了**才重建过渡；守护进程单独记下"屏幕上正在显示哪张"（不同于配置里写的那张，`set` 不改文件），重载或 `set` 发现要换的就是正在显示的，就不再换。

**连带的坑**：`[outputs.<name>] wallpaper` 会覆盖全局 `wallpaper`。往"所有显示器"写壁纸时只改全局键，那块显示器下次重载或重启就会退回旧图 —— 写"所有显示器"必须同时清掉各显示器自己的 `wallpaper`。

**怎么发现**：`daemon --trace` 的日志里，每次换图应当**恰好一行** `wallpaper → … (…, <effect> transition)`；出现两行，或者有一行而肉眼没看到过渡，就是这条。
